- 작성일: 2026-08-31
- 목적: 입력 경로를 고르기 전에 **실제 여정 전체**를 적고, `PROJECT.md`의 설계 원칙과 어긋나는 지점을 찾는다. `WORKPLAN.md §3`의 근거 문서.

## 1. 온보딩 — 설치부터 첫 기록까지

가장 이탈이 많이 나는 구간이다. 하루 10건을 기록하는 습관은 **첫 5분**에서 결정된다.

| 단계 | 사용자가 하는 일 | 마찰 | 처방 |
|---|---|---|---|
| O1 | LXC 설치 → `docker compose up` → 브라우저 접속 | 셀프호스터에겐 익숙 | stash proxmox 스크립트 그대로 |
| O2 | 첫 관리자 계정 생성 (`needsBootstrap`) | 낮음 | stash 부트스트랩 이식 |
| O3 | **가구 생성** | **"가구가 뭐지?"** — 계정 만들자마자 조직 개념을 물으면 뜬금없다 | **자동 생성한다.** 이름 기본값 "우리 집". 사용자는 **가족을 초대할 때** 처음 이 단어를 본다 |
| O4 | **반려동물 등록** | `PROJECT.md §4`의 `Pet`은 필드가 12개다. 다 물으면 여기서 이탈한다 | **이름 + 종만 필수.** 나머지(품종·성별·중성화·생일·입양일·등록번호·마이크로칩·색상·사진)는 전부 사후 편집. **3초 안에 끝나야 한다** |
| O5 | **홈 화면 진입** | 타일이 0개면 앱이 그 자리에서 죽는다 | **종별 기본 프리셋을 자동 생성한다.** 고양이면 사료·물·대변·소변·간식·구토·체중. 사용자는 아무것도 고르지 않았는데 홈이 채워져 있다 |
| O6 | 첫 기록 (타일 1탭) | — | 여기까지 오면 성공 |
| O7 | PWA 홈 화면 추가 | iOS는 공유 시트 안에 숨어 있어 스스로 못 찾는다 | 첫 기록 직후 **1회 안내**. 이후 다시 묻지 않음 |
| O8 | 사진 추가 | 필수로 하면 O4에서 이탈 | 홈에서 **부드러운 1회 유도**. 사진이 있으면 애착이 생겨 계속 쓴다 |
| O9 | 가족 초대 | 초대 링크는 URL에 토큰이 실린다 | **stash 패턴 채택** — 관리자가 계정을 만들고 임시 비밀번호를 1회만 응답. 링크 방식은 만들지 않는다 (K-6) |

### 온보딩에서 나온 설계 결정

1. **가구는 자동 생성하고 UI에서 숨긴다.** DB·API에는 `householdId`가 1급으로 존재하지만(K-1), 화면에는 가족 초대 전까지 등장하지 않는다. 다중 테넌시는 구현 개념이지 사용자 개념이 아니다.
2. **`Pet` 필수 필드는 `name` + `species` 둘뿐이다.** `PROJECT.md §2-1`("상세 입력은 항상 사후 편집으로 미룬다")은 이벤트에 대한 원칙이었지만 **등록 화면에도 그대로 적용한다.**
3. **반려동물 등록이 프리셋 생성을 트리거한다.** `EventType` 시드 → 종별 기본 프리셋 템플릿 → `Preset` 행 자동 생성. 빈 홈 화면은 존재해선 안 된다.

## 3. 인쇄 QR이 이기는 경우 — 정직한 검증

옹호 논거를 하나씩 세우고 무너뜨려 본다.

| 논거 | 검증 | 판정 |
|---|---|---|
| "타일이 많아지면 찾기 힘들다. QR은 물리적 위치가 곧 인덱스" | 프리셋 20개면 맞다. **고양이 1마리면 5~8개**고 한 화면에 들어간다 | **현재 해당 없음.** 12개 초과 시 재검토 |
| "다묘에서 대상을 확정해준다" | 진짜 이득. 탭에서 잘못 고르는 실수가 사라진다 | **미래 조건부** |
| "펫시터·부모님이 배울 게 없다" | 그 사람도 **로그인은 해야 한다**. 로그인시킬 정도면 타일도 가르친다 | **약함** |
| "라벨이 눈에 보여 기록을 떠올린다" | 효과는 있다. 하지만 **스티커의 효과**지 QR의 효과가 아니다 | **QR의 공로 아님** |
| "물건 앞에서 그 자리에 기록" | 타일도 그 자리에서 누른다 | **무효** |
| "연속으로 여러 건" | 사료+물+약이면 **3탭 < 카메라 켜고 3번 조준** | **타일이 이김** |
| "앱을 안 열어도 된다 — 기본 카메라" | 브라우저 로딩 + 세션 확인 + 확인 버튼이 붙는다 | **무승부 이하** |

### 유일하게 살아남는 것: 제품 바코드

**인쇄 QR과 제품 바코드는 다른 물건이다.**

- **인쇄 QR** = 우리가 만든 프리셋 지시자. 타일과 **정확히 같은 일**을 하면서 더 느리다 → 고유 가치 없음
- **제품 바코드** = 세상에 이미 존재하는 식별자. **타일로는 표현할 수 없는 정보**를 담는다(어느 약, 어느 사료). "실제로 그 물건을 손에 들고 찍었다"는 사실이 기록의 정확성을 보증한다

**스캐너는 살릴 가치가 있고, 라벨 인쇄 파이프라인은 지금 만들 이유가 없다.**

## 4. 진짜 경쟁자는 "앱을 여는 것" 자체다

`PROJECT.md §2-2`는 "앱을 열지 않고도 기록할 수 있어야 한다"고 못박았다. **타일도 QR도 이 원칙을 만족하지 못한다.**

| 순위 | 경로 | 잠금해제 이후 |
|---|---|---|
| 1 | **물리 버튼** (E) | **0** — 손이 이미 거기 있고 폰이 필요 없다 |
| 2 | **기기 웹훅** (F) | **0** — 사람이 없다 |
| 3 | manifest shortcut (B) | 롱프레스 + 2탭, 앱 셸 로딩 없음 |
| 4 | 홈 타일 (A) | 앱 열기 + 1탭 |
| 5 | 제품 바코드 (D) | 앱 + 스캐너 + 조준 — **정보를 더 담을 때만 값어치** |
| 6 | 인쇄 QR (C) | 같은 비용, **추가 정보 없음** |

**Phase 2의 HA 웹훅이 QR 파이프라인 전체보다 가치가 크다.** 다만 공개 전제에서 HA는 선택 기능이므로(K-10), HA 없는 사용자의 최선은 3순위다.

### manifest shortcut의 한계 — 확인이 필요하다

계획서에서 shortcut을 "프리셋 직행"으로 승격하려 했으나, **검증 없이 확정할 수 없는 문제가 있다.**

- `manifest.json`의 `shortcuts`는 **정적 목록**이다. 사용자별 프리셋을 담으려면 동적 매니페스트가 필요한데, 매니페스트는 **인증 없이 요청될 수 있어** 프리셋 이름이 노출된다.
- 더 큰 문제: 플랫폼에 따라 **shortcuts가 홈 화면 추가 시점에 고정**되어, 나중에 프리셋을 바꿔도 갱신되지 않을 수 있다.

**따라서 프리셋별 shortcut을 만들지 않는다.** 대신 **"빠른 기록" shortcut 하나**만 두고, 그 목적지를 타일 그리드만 있는 **초경량 페이지**로 만든다. 앱 셸 전체를 로딩하지 않는다는 이득은 그대로 남고, 동적 매니페스트 문제와 노출 위험은 사라진다.

> **P0에 검증 항목 추가**: 안드로이드/iOS에서 manifest `shortcuts`가 재배포 후 갱신되는가. 갱신되면 나중에 프리셋 직행을 재검토한다.

## 7. 설계 방향과의 정합성 검토

`PROJECT.md §2`의 원칙과 하나씩 대조한다.

### 7-1. "기록은 1탭 안에 끝난다" — ✅ 충족

타일 1탭 + 실행취소. 상세는 길게 누르기로 분리. S7(체중)·S9(병원)은 숫자·텍스트가 본질이라 예외이며, 원칙 위반이 아니라 **다른 종류의 시나리오**다.

### 7-2. "앱을 열지 않고도 기록할 수 있어야 한다" — ❌ **Phase 1 미충족**

**Phase 1에는 이 원칙을 만족하는 경로가 하나도 없다.** 타일·shortcut·스캔 전부 앱을 연다. 이를 만족하는 것은 물리 버튼(E)과 기기 웹훅(F)뿐이고 둘 다 Phase 2다.

> **이건 숨기지 말고 게이트의 판정 대상으로 삼는다.** 2주 실사용에서 F4("폰이 손에 없어서 못 기록")가 실제 이탈 원인이면, Phase 2의 우선순위는 웹훅이 1번이 된다. 아니라면 원칙 자체를 완화해야 한다 — **원칙이 현실과 다르면 원칙을 고친다.**

### 7-3. "홈 화면 = 입력 화면" — ⚠️ **S10과 충돌**

`PROJECT.md §5.1`은 홈을 입력 전용으로 두는데, S10("아침에 밥 줬나?")은 빈도 1~2회로 낮지 않다. 조회하러 다른 화면에 가야 하면 앱이 무거워진다.

**처방**: 홈 상단에 **오늘 요약 한 줄**을 둔다. `사료 2 · 물 1 · 배변 1`. 타일 그리드를 밀어내지 않는 높이로 제한하고, 탭하면 타임라인으로 간다. 입력 화면의 정체성을 해치지 않으면서 S10을 흡수한다.

### 7-4. "이벤트 스키마는 단일 테이블 + 타입 참조" — ✅ 충족

`Preset` 추가는 위반이 아니다. `Event`는 여전히 단일 테이블이고, `Preset`은 **입력 보조**이지 이벤트 저장소가 아니다. 오히려 `EventType.isQuickAction` 플래그를 없애 모델이 정리됐다.

### 7-5. "보안은 Phase 1부터" — ✅ 충족

K-1~K-10. 다만 **QR을 보류하면서 인증 경계 문제도 함께 사라졌다** — `/s/[code]` 랜딩이 Phase 1에 없으므로 K-7이 적용될 표면 자체가 없다.

### 7-6. "코드베이스는 영문, 사용자 대면은 한글" — ✅ 충족

공개 전제(§7.2)로 en 사전이 Phase 1로 올라왔다 (K-9).

### 7-7. 새로 발견된 충돌: JWT 수명

stash는 보안 강화로 90일 → **7일**로 줄였다. kibble이 그대로 쓰면 **2주 실사용 중 최소 1회 재로그인**이 발생한다. 게이트 기간에 마찰 하나가 통계적으로 반드시 끼어드는 셈이다.

**처방**: **30일로 늘린다.** 근거 — (a) `tokenVersion`으로 비밀번호 변경·로그아웃 시 **즉시 무효화**가 가능하다(stash 이식분), (b) 셀프호스트 + 가구 단위라 노출면이 좁다, (c) 재로그인 마찰이 게이트 판정을 오염시키는 비용이 더 크다. `/logout-all`과 비밀번호 변경은 그대로 전 기기 무효화한다.

### 인쇄 QR을 만들 조건 (트리거)

다음 중 **하나라도** 충족되면 그때 만든다. 그전에는 만들지 않는다.

1. 프리셋이 **12개를 넘어** 타일 그리드에 스크롤이 생긴다
2. 반려동물이 **2마리 이상**이 되어 대상 확정이 실제 문제가 된다
3. 본인 외에 **정기적으로 기록하는 사람**(펫시터·가족)이 생긴다

모델(`Preset` / `PresetCode`)은 Phase 1에 그대로 들어가므로, 그때 추가하는 것은 **라우트 2개와 인쇄 화면 하나**다 (K-8).
