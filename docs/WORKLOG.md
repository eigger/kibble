# 작업 기록

> **이 문서의 수명**: Phase 0~5 진행 중에만 유지한다. **정식 릴리스 전에 삭제하거나 `CHANGELOG.md`로 정리**한다.
>
> **목적 두 가지**
> 1. **회귀 방지** — 이미 검토하고 기각한 안을 다시 제안하지 않기 위해. 근거를 잃으면 같은 논의를 반복한다.
> 2. **큰 그림 유지** — 여러 장소·여러 세션으로 나뉘어 작업하므로, 이어받는 쪽이 "지금 어디까지 왔고 왜 이렇게 됐는지"를 이 문서 하나로 파악할 수 있어야 한다.

## 기록 규칙

**적는 것**

- 확정하거나 변경한 결정과 **그 근거**
- **기각한 안과 기각 사유** (가장 중요 — §1에 상시 유지)
- 조사·리뷰로 알아낸 사실 중 계획을 바꾼 것
- 다음 세션이 이어받아야 할 미완 항목

**적지 않는 것**

- 파일별 변경 내역 — git이 한다
- 시도했다가 버린 코드의 세부 — 결론만 §1에 남긴다
- 개인 정보, 실기록 인용 (공개 저장소다)

**결정이 바뀌면 `docs/WORKPLAN.md`를 먼저 고치고, 그 다음 여기에 기록한다.** 계획서가 단일 진실 원천이고 이 문서는 이력이다.

### 2026-09-05 — 저장 후 앱을 닫아도 올리기 (Background Fetch)

PR #62 머지 뒤, R89 재검토 조건을 Chromium에서 충족하는 쪽으로 열었다. **전 기기 전제는 그대로 기각.**

- 되는 곳: Chrome/Edge Android·데스크톱. 기록 POST 후 파일을 Cache에 담고 SW가 Background Fetch를 건다. 알림창 진행률은 UA가 그린다. 영상은 서버가 청크 순서를 강제하므로(409) 한 요청씩 직렬로 잇는다. 닫기 전에 persist가 끝나야 한다 — 그 짧은 구간만 "준비 중".
- 안 되는 곳: iOS 홈화면 PWA / Safari. 기존처럼 이 화면에서 올리고 배너 문구도 그대로다.
- 한 Background Fetch에 청크를 여러 개 넣으면 UA가 병렬로 보내 깨진다. 서버를 랜덤 액세스로 바꾸는 안은 API 변경이 커서 기각.
- 페이지가 죽으면 File/content URI는 사라지므로 persist는 `cache.put(Response(file))`로 디스크에 둔다. 영상 RAM 통째 복사는 하지 않는다. HEIC→JPEG는 canvas라 페이지에서 prepare한 뒤에 담는다.
- PR #63 리뷰: 청크 크기는 잡 레코드로만 흘린다(SW 리터럴 금지). 4xx는 `skipped`에 남겨 실패 배너에 띄운다(R59). 재시도는 `getToken()`으로 Bearer를 갱신한다. 옛 fetch settle은 `fetchId`가 다르면 버린다. 재시도는 페이지 경로와 같은 지수 백오프. pending만으로 "나가도 됩니다"를 말하지 않는다 — 진짜 in-flight(`fetchId`)일 때만. 실패 잡 GC·로그아웃 시 BF 저장소 정리는 이슈로 남긴다.
- PR #63 리뷰 2차: 실패 잡 GC와 로그아웃 정리를 이슈로 미루지 않고 넣었다. `createdAt` 기준 3일이 지난 `failed` 잡은 배너가 붙을 때 사본과 함께 지운다 — 원본은 갤러리에 있으므로 잃는 것은 "배너에서 다시 올리기"뿐이고, 그 대가로 수백 MB 사본이 무기한 남지 않는다. 주인 없는 사본도 같이 걷는다(스토어를 버렸거나 삭제가 끊긴 경우). 로그아웃은 `clearAppCaches()` 앞에서 `cancelAllBackgroundFetches()`를 부른다 — 캐시만 비우면 IndexedDB에 **동작하는 Bearer 토큰**이 남는다.
- 진행률: `prepareFailedJobForRetry`가 커서를 0으로 되감으면서 `bytesDone`도 `uploadedBytes`로 되감는다. 안 하면 재시도 뒤 loaded가 total을 넘어 배너가 100%에 붙박인다. `applyChunkDesync`도 `fileIndex`까지의 합이 아니라 실제로 올라간 파일의 합을 쓴다 — 4xx로 건너뛴 파일은 서버에 없다.
- `BF_DB_VERSION` 2. v1 잡에는 `chunkSize`가 없어 SW의 `jobChunkSize`가 던지고, 그 잡이 매 kick마다 죽으며 영구히 낀다. 업그레이드에서 스토어를 버린다.
- 영구 4xx(415 등)를 재시도가 다시 집는 건 **그대로 둔다**. 페이지 경로도 같고(R59), `skipped`를 남겨 재시도에서 빼면 이번엔 걷히지 않는 실패 배너가 된다. 제대로 고치려면 "이 파일은 형식이 안 맞습니다"를 따로 말해야 하는데 그건 새 UI다 (R90).
- 두 사본 드리프트는 타입 검사가 못 잡는다(`4e92f6d`에서 실제로 물었다). 테스트가 `public/sw-background-fetch.js`를 읽어 `BF_DB_VERSION` 일치와 청크 크기 리터럴 부재를 단언한다.

### 2026-09-05 — 저장은 즉시, 전송은 이 화면에서 + 그만두기

"백그라운드 업로드"가 앱을 나가도 된다는 뜻으로 읽혔다. 실제로는 **시트만 닫고 같은 탭에서** 올린다 (R89). 홈 버튼을 누르면 OS가 JS를 멈추므로 전송이 끊긴다.

실사용에서 사진·영상을 같이 올리다가 영상이 안 올라가고, 이력 삭제가 멈추고, 서버가 죽어서 재부팅했다.

- 영상 전체를 RAM에 복사하지 않는다. 수백 MB `arrayBuffer`는 탭을 멈추고 8초 타임아웃에 걸려 영상만 실패했다. 사진은 되고 영상은 안 되던 이유. 청크는 `slice`로 원본을 읽는다. **포기한 것:** 안드로이드 content URI 만료를 복사가 막아주던 경로. 긴 업로드 중간에 URI가 죽으면 그 영상은 실패하고, 같은 File로 다시 올려도 URI는 이미 죽었다.
- 업로드 `complete`가 ffprobe·포스터 ffmpeg를 기다려 폰이 99%에서 붙잡혔고, 직후 720p 변환이 기본 스레드 수로 2GB CT를 OOM 낼 수 있었다. 포스터·probe는 잡으로 옮기고, ffmpeg는 `-i` 앞(디코더)과 `libx264` 뒤(인코더) 둘 다 `-threads 1`. 포스터가 오기 전에 목록이 원본 `<video>`를 걸지 않게 pending/processing은 자리표시자.
- 배너 **그만두기**. 이력 삭제는 그 기록의 전송을 먼저 끊는다.

### 2026-09-05 — 업로드 재개가 재시작을 넘어 살아남게 + 이탈 경고

**배경**

앞 항목에서 384MB 조각이 남은 원인을 셋으로 정리했다. 상한은 낮췄고(150MB), 남은 둘이
이번 작업이다 — **재시작이 진행 중 업로드를 무효화하는 것**과 **화면 이탈이 곧 실패인 것**.

**1. 세션을 디스크에 남긴다 (R60 판정 변경)**

R60은 "재시작하면 처음부터 다시 올리면 되니 정상 동작"이라며 보류했었다. **전제가 틀렸다.**
384MB가 수십 분 올라가다 배포 한 번에 통째로 날아갔다 — 재개는 그때 가장 필요한데
정확히 그때 동작하지 않았다. 재검토 조건("다중 인스턴스")을 기다릴 문제가 아니었다.

다만 **DB·Redis는 여전히 과하다.** `tmp/<id>.json` 사이드카면 마이그레이션도 새 인프라도
없이 같은 결과가 나오고, 조각 파일과 수명이 같아 스윕도 한곳에서 끝난다. 단일 인스턴스
전제는 유지한다.

설계에서 중요한 결정 둘:

- **사이드카에는 변하지 않는 정보만 담는다.** 진행량은 `.part` 파일 크기에서 유도한다.
  기록해 두면 청크마다 디스크를 더 쳐야 하고, 크래시 시 실제 파일과 어긋난다 (R71).
  디스크가 언제나 정답이다
- **재개할 때 청크 경계까지 잘라내되, 자르는 곳은 쓰기 경로다.** `appendFile`은 원자적이
  아니라 도중에 죽으면 경계에 안 맞는 꼬리가 남는다. 그대로 이어 붙이면 조용히 깨진 영상이
  된다 — 최대 8MB를 다시 받고 만다 (R72). 다만 `receivedBytes === totalSize`면 자르지 않는다.
  마지막 청크는 경계에 안 맞는 게 정상이고 `complete`를 기다리던 상태이기 때문이다.
  **되살리기는 GET이라 계산만 하고 디스크를 건드리지 않는다** — 실제 잘라내기는
  `alignTempFileForWrite`가 PUT의 쓰기 잠금 안에서, append 바로 앞에 한 번 한다 (K-7, R78)

`getUploadSession`·`createUploadSession`·`deleteUploadSession`이 async가 됐다. 라우트의
`sessionForHousehold`도 마찬가지 — 가구 필터(K-1)는 되살린 뒤에 그대로 건다.

**2. 이탈 경고 + 화면 꺼짐 방지**

`lib/uploadGuard.ts` — 업로드가 도는 동안 사람의 이탈(`beforeunload`)과 기기의 절전
(Screen Wake Lock) 둘 다 막는다. 카운터라 배치와 개별 파일 양쪽에서 감싸도 안전하고,
`uploadEventAttachment`에 걸었으므로 오프라인 큐 재전송을 포함해 모든 업로드 경로가 덮인다.

이탈 경고 문구는 넣지 않았다 — 브라우저가 `returnValue`를 무시하고 자기 문구를 쓴다 (R73).
**iOS Safari는 `beforeunload`를 지원하지 않아 거기서는 보호가 없다.**

`lib/screenWakeLock.ts` — 폰을 내려놓으면 몇십 초 뒤 화면이 잠기고 전송이 멈춘다.
150MB면 몇 분이 걸리니 한 번은 겪는다. 이 API의 함정 셋을 전부 다뤘다:

- 페이지가 숨겨지면 브라우저가 **알아서 해제한다** — `visibilitychange`에서 다시 잡는다 (R75)
- 숨겨진 상태의 요청은 `NotAllowedError`로 거절된다 — 보일 때만 요청한다
- 요청이 비동기라 기다리는 사이 업로드가 끝날 수 있다 — 그때는 받자마자 놓는다

미지원·거절은 전부 조용히 넘어간다. 화면 유지는 있으면 좋은 것이지 업로드의 조건이 아니다.
배터리 우려로 넣지 않는 선택은 기각했다 (R74) — 실패한 업로드는 어차피 처음부터 다시
올리므로 오히려 배터리를 두 배로 쓴다.

**확인**

재시작 재개는 "모듈을 다시 import해 메모리 맵이 빈 새 프로세스를 만든다"로 시뮬레이션했다 —
반쯤 올라간 업로드 되살리기, 찢어진 청크 잘라내기, 완성된 파일 보존, 손상된 사이드카,

포스터 추출이 쓰는 `tmp/poster-*.jpg`도 스윕 대상에 넣었다(#54 리뷰 지적). 정상 경로에서는

### 2026-09-05 — 영상 포스터 프레임 + 업로드 상한 500MB → 150MB

**배경 — 진단이 뒤집혔다**

앞 항목에서 "업로드는 정상이고 재생 경로가 문제"라고 적었는데, 서버 디스크를 보니 **틀렸다.**

```
/app/uploads/events  → jpg만 있고 영상 없음
/app/uploads/tmp     → 384.0M  0c6679c0-....part   (Sep 4 01:22)
```

384.0MB는 정확히 `48 × 8MB`다. 청크 경계에서 딱 멈췄다 — 업로드가 중간에 죽고
조각만 남은 것이다. 재생이 안 된 게 아니라 **올라간 적이 없었다.**

Range 수정(앞 항목)은 그대로 유효하지만 이 증상의 원인은 아니었다. 원인은 구조다:

- 8MB 청크로 384MB면 48회 왕복 — 모바일에서 수십 분이 걸린다
- 그 사이 페이지를 벗어나거나 화면이 꺼지면 끝이다 (백그라운드 업로드가 없다)
- 세션은 프로세스 메모리에 있어 **API 재시작이면 재개도 불가능하다** (R60)
- 그런데 상한은 500MB라 시도 자체는 허용됐다

**중요**: 서버 압축(R64)은 이 문제를 못 고친다. 압축은 업로드가 **끝난 뒤** 일어난다.
384MB를 끝까지 올리지 못하는 게 문제라면 압축은 디스크만 아낄 뿐이다.

**한 일**

- **상한 500MB → 150MB** (R68). init 단계에서 바이트를 보내기 전에 413이 나가고,
  413은 이미 파일 단위 영구 거부라 그 파일만 실패하고 나머지는 올라간다.
  1080p 30fps 약 2분, 4K 30fps 약 40초 — 일지용 클립에는 충분하다
- **영상 포스터 프레임.** `Attachment.posterPath` 추가(마이그레이션 포함). 업로드 완료
  시 ffmpeg로 대표 프레임 한 장을 뽑아 저장하고, 목록·썸네일은 `<video>` 대신 그
  JPEG를 `<img>`로 쓴다 → **타임라인이 영상 바이트를 아예 받지 않는다.**
  재생(라이트박스)일 때만 진짜 영상을 가리킨다
- ffmpeg를 API 이미지에 추가. **프레임 추출에만 쓴다** — 재인코딩이 아니라 수백 ms다.
  없어도 앱은 동작한다(포스터가 null이 되고 `<video>`로 되돌아간다)
- 포스터는 `path`/`posterPath` 어느 쪽으로 찾히든 같은 `/file/*` 라우트로 나간다 (R70) —
  인증·가구 격리를 두 벌로 만들지 않는다. 삭제·휴지통 비우기도 포스터를 함께 지운다

**PR 리뷰 반영**

- **`-nostdin` 추가.** ffmpeg는 기본이 stdin 상호작용인데 Node가 stdin 파이프를 열어 둔다 —
  이게 없으면 빈 파이프를 기다리다 20초 타임아웃에 걸려 **모든 포스터가 조용히 실패할** 수
  있었다. 로컬에 ffmpeg가 없어 실행으로 못 잡았을 종류의 버그다. `execFile`은 `spawn`과 달리
  `stdio` 옵션을 못 받으므로 자식의 stdin을 직접 닫는 것으로 짝을 맞췄다
- multipart 경로(`saveEventAttachment`)도 포스터를 뽑는다. 웹은 영상을 항상 청크로 보내지만
  API 토큰으로 20MB 이하 영상을 직행시키면 그 경로만 포스터가 없어 목록이 갈라졌다
- 타임라인 썸네일에 영상 배지 추가 — 포스터가 붙은 뒤로는 사진과 구분이 안 됐다 (상세에는 이미 있었다)
- 문서 갱신: `PROJECT.md` §4에 `posterPath`, `api.md`·`deploy.md`의 상한 500 → 150.
  기본값이 바뀌었는데 문서가 500이면 env를 안 건드린 사람이 "왜 잘리냐"가 된다

**확인**

`npm test` api 165 / web 144 / shared 31 통과, `tsc --noEmit`·`prisma validate`·eslint 통과.

### 2026-09-05 — 큰 영상이 재생되지 않던 것 (Range) + 백업에서 첨부가 통째로 빠지던 것

**배경**

"용량 큰 영상 재생이 안 된다 — 업로드가 안 된 건지 다른 문제인지"라는 리포트.
영상 압축이 필요한지 검토하다가 **압축 이전의 문제 둘**을 찾았다.

**1. Range를 지원한 적이 없다**

`GET /api/attachments/file/*`가 `createReadStream`을 그대로 반환하고 있었다. 그래서
`Content-Length`도 `Accept-Ranges`도 없는 chunked 응답이 나갔다. 확실한 결과:

- `<video>`가 길이를 못 재고 진행바가 안 잡힌다
- **탐색이 매번 처음부터 다시 받는 일이 된다** — 큰 파일일수록 그대로 체감된다
- `preload="metadata"`가 무의미하다. 메타데이터만 받을 방법이 없어 목록에 영상 행이
  있으면 브라우저가 전송을 열고 버퍼링하다 끊는다
- iOS Safari는 `<video>`에 바이트 레인지를 요구한다 — 재생 자체가 실패하기도 한다

즉 **업로드는 정상이었고 재생 경로가 문제였다.** 첨부 행은 `complete`가 성공해 파일이
제자리로 옮겨진 뒤에만 만들어지므로, 목록에 영상이 **보이면 바이트는 이미 디스크에 있다.**
진단 기준으로 쓸 수 있다.

`lib/rangeRequest.ts`(파싱, 순수 함수) + `lib/sendFile.ts`(206·416·Content-Length)로 나눠
첨부와 펫 사진이 같은 헬퍼를 쓰게 했다. 캐시 헤더(`private, max-age=3600`)도 첨부에 붙였다 —
펫 사진에는 이미 있었다. 다중 구간은 지원하지 않는다 (R66).

**2. 백업에 사진·영상이 하나도 안 들어갔다**

`backup.ts`가 `entry.isFile()`인 최상위 항목만 복사하고 있었다. 그런데 첨부는
`uploads/events/`, 펫 사진은 `uploads/pets/` — **둘 다 디렉터리다.** 파일이 UPLOAD_DIR
루트에 평평하게 있던 시절 코드가 서브디렉터리 도입 후 갱신되지 않은 것으로 보인다.
내보내기·복원 양쪽 모두 같은 모양이었다.

`fs.cp({recursive:true})`로 바꾸고, 로직을 `lib/backupFiles.ts`로 빼 DB 없이 테스트할 수
있게 했다 (백업 통합 테스트는 `*.integration.test.ts`라 기본 실행에서 제외된다).
청크 조각(`tmp/`)과 이전 아카이브(`*.tar.gz`)는 계속 제외한다.

**영상 압축은 하지 않았다** — R64에 근거와 재검토 조건을 남겼다. 요약하면 Range·포스터
프레임·상한 조정을 먼저 하는 편이 이득/비용이 훨씬 낫고, 트랜스코딩은 큐·워커까지
한 세트라 Phase 1 게이트 중에 넣을 무게가 아니다.

**확인**

`npm test` api 161 통과(Range 라우트 6케이스·파싱 12케이스·백업 파일 5케이스 신규),

### 2026-09-04 — 갤럭시 다중 업로드: 준비 단계가 0%에서 멈춘 뒤 나머지 포기

서버 로그에는 첨부 POST가 없거나 성공만 있었다. 권한(MEMBER) 문제가 아니라
**업로드 직전 준비**에서 막힌 것이다.

**알아낸 것**

1. 안드로이드 다중 선택의 File은 content URI 포인터다. 1장을 변환·전송하는 수 초
   동안 2장째 URI가 만료되면 `NotReadableError`.
2. 그 오류는 HTTP 4xx가 아니라서 R59의 "일시 장애면 중단"에 걸려 나머지를 포기했다.
   Chromium은 같은 실패를 `TypeError("… could not be read")`로 감싸기도 한다.
3. `createImageBitmap`에 타임아웃이 없었다. 멈추면 0%처럼 보이는 준비 단계에서
   대기하고, 타임아웃만 걸고 Abort를 안 하면 48MB 비트맵이 백그라운드에 남는다.
4. 준비 실패는 `console.error`로 안 남겨서 이슈 등록에도 안 붙었다.

**한 일**

- 선택 직후 **병렬** `snapshotFile` — 순차 arrayBuffer는 뒤 파일 URI를 그 사이에 죽인다.
- `NotReadableError`와 "could not be read" TypeError는 파일 하나 거부로 취급.
- `createImageBitmap`에 20초 타임아웃 + `AbortSignal.timeout`. 한 장이 멈추면
  이후 장은 리인코딩을 건너뛰고 원본 JPEG를 올린다 (서버가 줄인다).
- `arrayBuffer`에도 같은 타임아웃 — 권한 회수된 URI에서 읽기가 안 끝나는 기기 대비.
- 준비 실패는 `console.error("[uploadPrep] …")`.
- 버전 0.8.3

**남은 틈**: 미리보기 `<img>`가 원본 해상도를 디코드한다. PWA가 앨범을 여는 동안
렌더러가 죽으면 스냅샷도 못 한다. 이 패치는 URI 만료·디코더 hang을 흡수하지,
프로세스 킬을 되돌리지는 않는다.

**다음**: v0.8.3 배포 후 그 갤럭시에서 여러 장 재시도. 실패하면 이슈 등록 본문의 `[uploadPrep]` 줄을 본다.

### 2026-09-04 — 첨부 업로드 진행률 + 영상 × 버튼 터치

**알아낸 것**

영상 썸네일은 `<video>`라 iOS/안드로이드가 네이티브 합성 레이어로 그린다. 22px × 버튼이

- ko/en 동시 (K-9). 버전 0.8.2

**다음**: 실기기에서 영상 썸네일 ×가 바로 제거되는지, 큰 영상 업로드 중 %가 움직이는지

### 2026-09-04 — 사진·영상 업로드 신뢰성 (다중 업로드·중간 에러·생성 토스트)

**배경**

사용자 리포트 셋: ① 사진·영상 다중 업로드가 안 된다 ② 업로드 중간에 에러가 잦다
③ **처음 등록인데 "수정되었습니다"라고 뜬다**.

코드를 훑어보니 ①과 ②는 별개 버그가 아니라 하나의 사슬이었다.

**알아낸 것 — 계획을 바꾼 사실**

1. **sharp 프리빌트 바이너리는 HEIC을 열지 못한다.** `sharp.format.heif.input.fileSuffix`가
   `['.avif']`뿐이다 — libheif는 들어 있지만 HEVC 디코더가 라이선스 때문에 빠져 있다.
   그런데 서버 허용 목록에는 `image/heic`/`image/heif`가 있었다. 즉 **받아놓고 100% 400**.
   아이폰 사진이 전부 여기서 죽었다.
2. **`accept` 목록이 상황을 악화시키고 있었다.** iOS Safari는 `accept`에 `image/heic`이
   있으면 원본 HEIC을 넘긴다 — 빼면 JPEG로 변환해 준다. 스스로 깨지는 경로로 몰고 있었다.
3. **첫 실패에서 나머지 파일을 시도조차 하지 않았다.** 그래서 ①로 보였다.
4. **청크 업로드 재시도가 사실상 작동하지 않았다.** ⓐ `fetch`가 던지는 네트워크 오류는
   재시도 루프 밖으로 그대로 빠져나갔다(모바일에서 가장 흔한 실패인데). ⓑ 서버가 409에
   실어 보내는 `expectedIndex`를 클라이언트가 읽지 않아, 응답만 유실되면 같은 인덱스를
   3번 반복하고 영구 실패했다. ⓒ 4xx도 똑같이 3번 두드렸다.
5. **③은 문구 버그.** 생성 경로가 수정 경로와 같은 `eventDetailSaved` 키를 쓰고 있었다.
6. 덤으로 찾은 것: 새 기록 생성 시 **첨부 업로드가 타임라인 삽입보다 먼저** 실행돼,
   `mergeEventAttachments()`가 아직 목록에 없는 이벤트를 찾다 실패 → 새 기록에 사진이
   새로고침 전까지 안 보였다.

**한 일**

- `apps/web/lib/uploadPrep.ts` (신규): 업로드 직전 MIME 보정(빈 `type`을 확장자로 되살림 —
  안드로이드 파일 제공자 대응)과 이미지 canvas 리인코딩(1600px JPEG, 서버 파이프라인과 동일 값).
  HEIC → JPEG 변환과 전송량 감소를 한 번에 해결한다. 변환 불가 환경이면 원본을 그대로 올린다 (K-12)

### 2026-09-02 — 첫 Proxmox 배포에서 API 미기동 (v0.2.1)

**증상**

첫 실전 배포. 관리자 생성 화면 대신 로그인 화면이 뜨고, 어떤 계정으로도 로그인되지 않았다.

**원인 — 시드 실패가 기동을 막았다**

compose의 api 커맨드가 `migrate deploy && prisma db seed && node …` 였다. `prisma.config.ts`의
`seed: "tsx prisma/seed.ts"`는 **실행 시점 cwd 기준**으로 풀린다 — 컨테이너 cwd가 `/app`이라
`/app/prisma/seed.ts`를 찾다 `ERR_MODULE_NOT_FOUND`. `&&` 체인이라 **API가 아예 실행되지 않았다.**
경로를 맞췄어도 `seed.ts`가 `apps/api/src`를 import하는데 이미지에는 `dist`만 있어 또 실패한다.

여기에 **로그인 페이지가 실패를 삼켰다.** `/api/auth/bootstrap/status`가 실패하면 전부
`needsBootstrap: false`로 흡수해 "관리자가 이미 있다"와 "서버에 못 닿는다"가 같은 화면이 됐다.
그래서 증상이 원인을 전혀 가리키지 않았다.

**한 일**

- compose(prod·dev)의 기동 커맨드에서 `prisma db seed` 제거 (R36). 시스템 EventType은
  `index.ts`가 기동 시 직접 시드하므로 원래 중복 단계였다
- 로그인 페이지가 **도달 실패와 부트스트랩 불필요를 구분**한다. 못 닿으면 안내 + 재시도 버튼
- `prisma.config.ts`에 seed 경로가 cwd 기준이라는 주석 — 같은 함정을 다시 밟지 않도록
- **시드가 기본 관리자를 만들지 않는다.** `ADMIN_PASSWORD`가 있을 때만 생성한다.
  기본값 `admin@example.com` / `changeme123`은 공개 저장소에 그대로 있었고, 한 번이라도
  시드가 돌면 `user.count()`가 1이 되어 **부트스트랩 화면이 영영 열리지 않는다**
- `.env.example`·`deploy.md`에 `ADMIN_*` 문서화(원래 문서에 없던 조용한 기본값이었다),
  `deploy.md` §6.1·§6.2에 기존 설치 대응 절차

**교훈**

`A && B && C` 기동 체인에서 B가 개발 전용 도구면 C가 볼모가 된다. 그리고 **부팅 경로의
fail-open은 진단을 지운다** — 이번엔 증상만 보고는 원인을 좁힐 수 없었다.

### 2026-09-02 — 오프라인 큐를 사용자 단위로

**문제**

`OfflineSync`가 IndexedDB 큐를 무조건 flush했다. 401은 영구 거부(400·404·409·422)에 없어서
큐에 남는다 — 그래서 **A가 오프라인으로 기록 → 로그아웃 → B가 로그인**하면 A의 미전송 기록이
B의 가구로 들어갔다. 기기 공유가 이 앱의 기본 시나리오(§7.12)라 가정상의 경로가 아니다.
K-1을 서버에서 아무리 지켜도 클라이언트가 남의 기록을 내 세션으로 보내면 소용이 없다.

**한 일**

- `QueuedEvent.userId` 추가. `enqueueOfflineEvent`가 적재 시 소유자를 박고,
  `listOfflineEvents(userId)`·`getOfflineQueueCount(userId)`·`flushOfflineQueue(userId)`가
  본인 것만 다룬다
- `OfflineSync`는 `useAuth()`로 사용자를 받는다 — **로그아웃 상태에서는 flush도 카운트도 하지 않는다**
- IndexedDB `DB_VERSION` 1 → 2. 배포 전이므로 v1 항목을 이전하지 않고 스토어를 새로 만든다 (R35)
- 삭제는 하지 않는다 — 본인이 다시 로그인하면 그대로 전송된다. 데이터 손실 없음

**설계 메모**

`pendingUploads`(청크 이어올리기, localStorage)는 손대지 않았다. `uploadId`가 서버에서
가구로 스코프되므로 다른 사용자가 이어올리려 하면 404가 나고 새 세션으로 다시 시작한다.

### 2026-08-31 — PR #1 리뷰 반영 (문서 단계 수정)

에이전트 리뷰 10건 중 문서로 해결 가능한 전부를 반영했다. 코드 이전이므로 문서에서 고쳤다.

**확정한 것**

- **시스템 `EventType`은 부분 유니크 인덱스가 필요하다.** `@@unique([householdId, key])`는 `householdId = null`인 시스템 행에 걸리지 않는다 — PostgreSQL이 UNIQUE에서 NULL을 서로 구별되는 값으로 보기 때문. 시드 재실행 시 조용히 중복된다. 초기 마이그레이션에 `CREATE UNIQUE INDEX ... WHERE "householdId" IS NULL`을 raw SQL로 넣고, 시드는 **`upsert` 대신 `findFirst` → `create`**로 쓴다 (`upsert`는 복합 unique에 NULL이 끼면 `where`를 만들 수 없어 실행 자체가 불가). `PROJECT.md §4`·`seed-event-types.md §1.1`
- **둘째 반려동물 등록 시 프리셋을 중복 생성하지 않는다.** 프리셋은 `petId = null`(가구 전체)이므로 등록마다 삽입하면 "사료"가 두 개가 되고 `isStarter`가 6개가 되어 G-1이 깨진다. 이미 있는 `eventTypeId`는 건너뛰고, **`isStarter`는 첫 등록 때만** 설정한다. `existing` 집합에 `archivedAt` 조건을 걸지 않는다 — 사용자가 숨긴 칩이 되살아나면 안 되기 때문. `seed-event-types.md §4.0`
- **시드 프리셋의 `label`은 i18n 키를 저장한다** (`eventType.meal`). 한글 리터럴을 넣으면 en 사용자가 첫 실행부터 한글 칩을 본다 (K-9 위반). 사용자가 이름을 고치면 리터럴로 바뀌고 그때부터 로케일을 따르지 않는 것이 맞다. 판별은 `eventType.`/`preset.` 접두사. `seed-event-types.md §3.1`
- **파싱 상대 시각 기준값을 한 표로 고정**했다 (아침 08:00 / 저녁 19:00 …). **P1-24의 시각 빠른 버튼도 같은 표를 쓴다** — 두 경로가 다르면 타임라인 정렬이 어긋난다. `parsing-benchmark-public.md`
- **`needsReview`가 true가 되는 조건 4가지를 확정**했다 (타입 후보 복수 / 상대 시각 추정 / 범위 환산 / `note` 흡수). `~정도`·`~인듯` 같은 근사 표현은 그 자체로는 true가 아니다 — 사용자는 원래 그렇게 쓴다(J10). `WORKPLAN §5.6`의 게이트 지표가 측정 가능해졌다
- **범위 수량은 중간값**, 앞자리 생략(`7~80` → `70~80`)은 보정 후 중간값. 규칙 없이 기대값만 있어 테스트가 불가능했던 것을 고쳤다
- **개인 픽스처 경로는 `fixtures/private/` 하나**로 통일했다

**기각한 것** → §1에 R23 추가

**고친 문서 정합성**

- 벤치마크의 `rawLine` → `rawText`로 통일 (`PROJECT.md §4` 필드명). 여러 줄일 때 각 이벤트는 **그 줄만** 담고 `entryId`로 묶는다
